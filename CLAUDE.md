## 1. Суть задачи за 30 секунд
24-часовой хакатон. Нужен прототип системы, которая **оценивает работу оператора поддержки брокера по чек-листу с помощью LLM**:
1. **Оценка**: пользователь настраивает чек-лист → загружает диалог(и) → запускает оценку → видит по каждому критерию ответ, баллы, вес, объяснение и **реплику-доказательство** (кликабельную). Итог считается с перераспределением весов при N/A. Грубые ошибки — отдельный флаг.
2. **Работа с результатом**: список → карточка (транскрипт + результат, плеер у звонков) → **апелляция** по критерию с комментарием → **проверяющий** подтверждает/меняет оценку с причиной → пересчёт; видны исходная оценка, решение, финал.

Регистрация/авторизация не нужны: роли «Оператор» и «Проверяющий» — переключатель в UI.

## 3. Как отбирают (top-50)
1. **Главное — точность**: на 10 новых транскриптах наши оценки сравнивают с эталоном (Ground Truth).
2. Функциональность и уникальные фичи, качество реализации.
3. Удобство интерфейса и процесса.
4. Корректность процесса: система реально анализирует диалоги и применяет критерии (не заготовки).
5. Разнообразие архитектур между командами (локальные LLM vs облачные). Мы — облачная (OpenAI).
Для платной модели в README указать название и примерную стоимость одной оценки.

**Уточнение от команды Freedom Broker (07.11, важно):**
- Идеального совпадения с экспертами до балла не ждут — смотрят на **близость и адекватность** оценки в целом. Не тратить время на угадывание их внутренней методики.
- Главное: система **осмысленно анализирует новые диалоги**, применяет чек-лист и даёт **логичные, обоснованные и воспроизводимые** оценки.
- N/A, грубые ошибки, неполные данные и спорные случаи — обрабатывать разумно. **Если информации недостаточно — не придумывать факты**, а честно помечать неуверенность.

**Второе уточнение (07.11) — про внешний вид:** продукт для крупной компании; пользователи — руководители, директора, специалисты контроля качества и рядовые сотрудники. Неудачный стиль снижает ценность для бизнеса; мультяшность, «игровое» оформление не подходят. Нестандартные решения приветствуются, но мыслить как создатель корпоративного продукта.
→ Для нас: корпоративный стиль в палитре Freedom (макет `docs/mockups/card-v2.html`), никакой геймификации; три сценария использования — **руководитель** (экран «Обзор»: сводка качества, риски, слабые критерии), **специалист контроля качества** (проверка диалогов и апелляций), **оператор** (свои оценки, подача апелляции).

Что из этого следует для нас:
1. Не переобучать промпт под DEV: эталон на 15–20 диалогах для проверки здравого смысла, а не для погони за десятыми.
2. **Воспроизводимость:** temperature 0 и фиксированный seed, версия промпта (`prompt_version`) хранится в каждой оценке; повторная оценка того же диалога должна давать тот же результат — показываем это в интерфейсе.
3. **«Недостаточно данных»:** если модель не может уверенно решить по критерию, она не выдумывает доказательство, а ставит `confidence: "low"` и `uncertainty_reason`; такие оценки получают `needs_review` и уходят человеку. Это не N/A (N/A — только по условию чек-листа).
4. Каждое утверждение в объяснении опирается на реальную реплику (проверка доказательств обязательна).
5. Звонки: в промпте прямо сказать, что текст — автотранскрипция с ошибками; не штрафовать за искажения слов, маски `[... скрыто]` и паузы; реплики на удержании не оценивать.

## 5. Данные
**API организаторов (временный)** — это один GET-эндпоинт (HTTP-триггер Power Automate); набор выбирается параметром `group_id`. `DEV` — набор для разработки, у контрольного будет другой `group_id`.
- Адрес содержит подпись доступа (`sig=...`) → **он секретный, в репозиторий не коммитим**. Лежит в `.env` как `ORG_API_URL` (без `group_id`; бэкенд добавляет `&group_id=<значение из UI>`). Взять адрес: кнопка «Открыть GET для DEV» на стр. 3 гайда участника (PDF организаторов) или у участника B.
- Локальная копия ответа: `data/dev.json` — **в `.gitignore`** (данные организаторов, 5 реальных звонков). Скачать: `curl.exe "%ORG_API_URL%&group_id=DEV" -o data/dev.json` или через `POST /api/datasets/import`.
- PDF организаторов (гайд, чек-лист) лежат локально в `docs/materials/` — тоже в `.gitignore`. Всё нужное из них уже перенесено в этот файл и `data/checklists/default.json`.

Формат ответа:
```json
{ "error": "", "isSuccess": true, "data": { "dataset_group_id": "DEV", "total_records": 65,
  "records": [ { "conversation_id": "p1-ru-001", "channel": "agent chat", "language": "RU",
    "transcript": [ { "timestamp": "00:02", "speaker": "operator", "text": "Здравствуйте!" } ],
    "audio_url": null } ] } }
```
- 65 диалогов: 60 синтетических чатов (30 RU, 15 KZ, 15 EN; id `p1-xx-NNN`) + 5 реальных звонков RU (`p4-ru-00N`).
- Роли: `client`, `operator`, `bot`, `system`. Оценивается **только оператор**; бот и system — контекст.
- Время: чаты `MM:SS`, звонки ISO 8601 с часовым поясом. Исходные метки сохранять.
- `audio_url`: null у чатов, ссылка у звонков (плеер).
- Типичный чат: клиент → бот AIM (приветствие + согласие на ПДн — шаблон) → бот отвечает шаблонно → клиент просит оператора → `system: Эскалация на оператора` → оператор.
- Ключевые system-события: «Личность клиента подтверждена» / «Клиенттің жеке басы расталды» / «Customer identity verified» (→ критерий 03); «Клиент покинул чат», «Соединение с клиентом прервано», «Connection to customer lost», «Оператор закрыл чат» (→ критерий 07 и N/A).
- Звонки: шумная автотранскрипция, маски `[Имя скрыто]`, `[Персональные данные скрыты]`, `[Данные идентификации скрыты]` (маска имени = оператор представился), IVR-бот, дубли реплик, **удержание**: реплики оператора между «Клиент находится на удержании» и «Клиент больше не находится на удержании» — разговор с коллегой, клиент их не слышит.

## 6. Чек-лист (стартовая конфигурация: `data/checklists/default.json`)
| # | Критерий | Тип | Вес | N/A |
|---|---|---|---|---|
| 01 | Установление контакта: поздоровался на языке клиента **и** представился в первом ответе | да/нет | 10 | нет |
| 02 | Выявление потребности: учёл известные детали, уточнил недостающее до ответа | да/нет/N/A | 15 | данных хватало с начала |
| 03 | Идентификация: подтверждена до раскрытия данных / защищённого действия | да/нет/N/A | 20 | запрос не требовал идентификации |
| 04 | Корректная и полная консультация | шкала 0/5/10/15/20 | 20 | чат закончился до формулировки запроса |
| 05 | Эмпатия и клиентоориентированность | да/нет | 15 | нет |
| 06 | Управление диалогом, скорость, грамотность | шкала 0/4/7/10 | 15 | нет |
| 07 | Завершение: итог или предложение помощи **и** прощание | да/нет/N/A | 5 | чат оборвался до возможности завершить |
| 08 | Грубые ошибки: оскорбление / платная услуга в обход компании / раскрытие конфиденциальной информации | флаг, без баллов | — | — |

**Расчёт (строго, делает код, не LLM):** да = полный вес, нет = 0; шкала → `вес × ступень / максимум`; критерии с N/A исключаются, их вес пропорционально перераспределяется так, чтобы максимум остался 100; итог округляется до 2 знаков; если применимых критериев с весом нет — итог не считается; грубые ошибки — отдельная отметка. Порог первой реакции 3 мин, теги и вложения в оценку **не входят**.
**«Нет» vs N/A:** «Нет» — действие было нужно, но пропущено/сделано неправильно; N/A — только по условию критерия. Общий вопрос о тарифах не требует идентификации; если требовалась проверка личности перед защищённым действием и она не подтверждена — «Нет».
**Обоснование:** конкретная реплика/системное сообщение + что оно подтверждает; для пропущенного действия — где оно ожидалось; для N/A — какое условие выполнено. Пример: «Завершение — Нет. После ответа оператор закрыл чат без прощания. Основание — последняя реплика оператора и сообщение о закрытии чата».

## 7. Архитектура и структура репозитория
```
backend/
  app/main.py            FastAPI, /api/*, раздача frontend/ как статики
  app/db.py              SQLite: conversations, checklists(versions), evaluations, appeals, jobs
  app/services/
    fetcher.py           адаптер API организаторов + нормализация (index, offset_sec, on_hold)
    prompts.py           build_prompt(checklist, conversation) — динамически из чек-листа
    llm_client.py        вызов OpenAI gpt-6.1-sol, Structured Outputs (JSON), usage/cost
    evaluator.py         вызов LLM → валидация → проверка доказательств → rules → scoring
    rules.py             детерминированные сигналы грубых ошибок и идентификации
    scoring.py           расчёт баллов (см. §6) + tests
  tests/
frontend/
  index.html  css/  js/api.js  js/views/*.js  js/components/*.js  mocks/*.json  d365-demo.html
data/  dev.json  checklists/default.json  gt/dev_labels.json
eval/  accuracy.py       сравнение с нашим эталоном
docs/  PLAN.md  API_CONTRACT.md  RESEARCH.md
```
- ID реплики = индекс в массиве `transcript`; якорь во фронте `#msg-{index}`.
- Все схемы и эндпоинты — **только по `docs/API_CONTRACT.md`**. Менять контракт — только договорившись с напарником.

## 8. Наши фишки (чем выделяемся — см. RESEARCH.md)
1. **Радар комплаенса**: грубые ошибки ловят LLM + детерминированные правила; расхождение → `needs_review`; красная метка и фильтр «Риски».
2. **Проверка доказательств**: бэк проверяет, что указанная реплика существует и содержит цитату.
3. **Лента событий** над транскриптом: эскалация → приветствие → идентификация → раскрытие данных → завершение/обрыв.
4. **«Что клиент уже сказал боту»**: переспрос известного = провал критерия 02.
5. **Версии чек-листа + «было → стало»** после смены критерия.
6. Калибровка: свой эталон на DEV + метрика совпадения, паритет RU/KZ/EN.
7. Готовность к D365: самостоятельный компонент + демо-страница.

## 10. Правила для Claude в этом репозитории
- Не трогай чужую зону (A — `backend/`, B — `frontend/`) без явной просьбы пользователя.
- Не коммить `.env`, ключи, `*.db`, `data/dev.json`, PDF организаторов, адрес API организаторов. Перед каждым пушем: `git grep -nE "sk-|sig="` должен быть пуст. Коммить часто, в свою ветку (`backend/*` или `frontend/*`), перед пушем `git pull --rebase origin main`.

- Баллы считает только `scoring.py`; LLM возвращает ответы, ступени, индексы реплик, объяснения.
- Фронт — без фреймворков и CDN-зависимостей (ES-модули). Демо-режим: `python -m http.server 5173` в корне → `/frontend/index.html` (данные из `frontend/js/mock/`). Живой режим: FastAPI раздаёт `frontend/` и `/api`; `?live=1` / `?mock=1` переключают режим.
- **Абука:** FastAPI раздаёт `frontend/` как статику (корень `/` → `frontend/index.html`) и API под `/api`. Интерфейс в живом режиме берёт всё, включая чек-лист, только из `/api/*` строго по контракту. Правила дизайна — `docs/DESIGN.md`.
