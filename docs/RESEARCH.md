# Ресерч: боли заказчика (Freedom Broker) и что из этого следует для CQA

> Источники: гайд участника, чек-лист качества чатов, критерии отбора, все 65 диалогов DEV-набора, открытые данные (ссылки внизу).
> Дата: 2026-11-07. Дедлайн (стоп-код): 2026-11-08 12:00 по Астане.

---

## 1. Кто заказчик и в каком он контексте

- **Freedom Broker (Freedom Finance)** — брокер в составе Freedom Holding Corp. (NASDAQ: FRHC, регулятор SEC), ~874 тыс. брокерских счетов, капитализация холдинга ~$11 млрд. Регулируемый финансовый бизнес: идентификация клиента, тайна персональных данных, запрет на «частные» инвестсоветы сотрудников.
- **Контакт-центр гибридный**: клиента сначала встречает AI-бот **AIM**, при необходимости бот эскалирует на живого оператора. Каналы — чат на сайте/в приложении, мессенджер Aitu (подключён в марте 2026: бот → оператор) и телефон (IVR → оператор, запись + автотранскрипция).
- **Три языка обслуживания**: RU, KZ, EN. Один и тот же чек-лист должен работать на всех.
- **CRM — Microsoft Dynamics 365** (прямо указано в задании: интерфейс должен адаптироваться как HTML-компонент D365). Транскрипты отдаются через Power Automate (временный API организаторов — это HTTP-триггер Power Automate).

## 2. Боли заказчика

### Б1. Ручной контроль качества покрывает крошечную долю диалогов
Отраслевой ориентир — вручную оценивается **1–5 % обращений** (в разных источниках 1–2 %, 1–3 %, 2–5 %). Остальные 95+ % — «слепая зона»: грубые нарушения и системные ошибки операторов просто не видны.
→ **Нужно:** пакетная автооценка 100 % диалогов, быстрая (10 контрольных диалогов — за минуты).

### Б2. Субъективность и рассинхрон оценщиков
Разные супервайзеры по-разному трактуют «Нет» vs «N/A», «представился» vs «поздоровался», «15» vs «10» по шкале. Отсюда — споры операторов и недоверие к оценкам. Сам чек-лист содержит памятку «Чем Нет отличается от N/A» — значит, на этом спотыкаются люди.
→ **Нужно:** детерминированные правила, единые для всех языков; LLM отвечает только на вопрос «что произошло», а **баллы, перераспределение весов и округление считает код**.

### Б3. Оценки без доказательств невозможно защитить
Оператор оспаривает оценку → супервайзер заново перечитывает весь диалог. Нет ссылки на конкретную реплику, нет «где ожидалось действие».
→ **Нужно:** по каждому критерию — реплика-доказательство (кликабельная, со скроллом и подсветкой), для пропущенного действия — проверенный участок, для N/A — какое условие неприменимости выполнено.

### Б4. Апелляции живут в почте/мессенджерах, без истории
Нет единого места «оспорил → проверяющий посмотрел → решение → пересчёт». Теряется исходная оценка, причина изменения, кто решил.
→ **Нужно:** workflow апелляции как отдельные действия (оператор / проверяющий), аудит-трейл: исходная AI-оценка → решение → финал, автоматический пересчёт итога.

### Б5. Чек-лист меняется, а менять его должны не разработчики
Регламенты меняются (новые продукты, требования регулятора). На контрольном этапе организаторы **заменят один критерий** и попросят применить через UI — это прямая проверка этой боли.
→ **Нужно:** редактор чек-листа (критерии, формулировки, вес, тип ответа: да/нет или шкала, N/A вкл/выкл, шкала для числовых), версии чек-листа, промпт собирается **динамически** из конфигурации — никаких захардкоженных критериев.

### Б6. Комплаенс-риски и мошенничество операторов (самая дорогая боль)
В DEV-наборе заложены ровно те сценарии, которых брокер боится:
- **предложение «скинуть деньги на карту, я сам вложу»** (p1-ru-022);
- **платная частная консультация по личному номеру** (p1-ru-023, p1-kz-013, p1-en-013);
- **раскрытие данных о счёте без идентификации** («вижу ограничение на вывод на вашем счёте» до проверки личности: p1-ru-009, p1-kz-015, p1-en-014);
- **оскорбление клиента** («Вы вообще читать умеете?» p1-ru-029).
Для регулируемого брокера это регуляторный и репутационный риск, а не просто «низкий балл».
→ **Нужно:** грубые ошибки — отдельный флаг (без баллов), заметный в списке (красная метка, фильтр), с доказательством.

### Б7. Мультиязычность, особенно казахский
Супервайзер должен владеть языком диалога; LLM заметно слабее на казахском, чем на английском/русском (подтверждают бенчмарки KazMMLU и пилот NU «Do LLMs speak Kazakh?»). В казахских чатах встречаются русские названия разделов («Меню → Поручения…») — это норма интерфейса, а не ошибка языка.
→ **Нужно:** модель с хорошим казахским; оценка «поздоровался на языке клиента» с учётом этого; объяснения выводить на языке интерфейса (RU), а цитаты — в оригинале.

### Б8. Гибрид «бот + оператор»: оценивать нужно только оператора
Реплики бота и system-события — контекст. Но они критичны для оценки: если клиент уже объяснил проблему боту, а оператор спрашивает «Чем могу помочь?» / «Где именно ищете?» — это провал выявления потребности (p1-ru-014, p1-ru-026, p1-kz-008). Идентификация подтверждается **системным** сообщением («Личность клиента подтверждена» / «Клиенттің жеке басы расталды» / «Customer identity verified»). Обрыв чата — тоже system («Клиент покинул чат», «Connection to customer lost») и он определяет N/A.
→ **Нужно:** передавать LLM весь контекст с ролями и индексами, но явно указывать, что оценивается оператор; системные события — ключ для критериев 03 и 07.

### Б9. Звонки — грязные данные
5 реальных звонков: шумная автотранскрипция («Сами тебе Фридом брокер за кошки…» = приветствие IVR на казахском), маскирование ПДн (`[Имя скрыто]`, `[Данные идентификации скрыты]`), IVR-меню, дубли реплик, удержание (hold) и консультация с коллегой. **Во время удержания оператор говорит с коллегой — клиент этого не слышит** (p4-ru-002, реплики между «Клиент находится на удержании» и «Клиент больше не находится на удержании») — эти реплики нельзя оценивать как общение с клиентом. Время у звонков — ISO 8601, у чатов — MM:SS. Для дикции/интонации нужен звук (транскрипт не годится).
→ **Нужно:** нормализация (маска ПДн = «представился», hold-сегменты помечать), плеер с переходом на таймкод реплики, честная пометка «интонация не оценивается по транскрипту».

### Б10. Встраивание в Dynamics 365 и данные внутри периметра
У Microsoft есть собственный Quality Evaluation Agent в D365 Contact Center, но он требует Copilot-кредитов, **согласия на перемещение данных между регионами** и привязан к экосистеме. Для казахстанского брокера с персональными и финансовыми данными (Закон РК «О персональных данных и их защите», требования АРРФР к проверке клиентов) это аргумент за собственное решение, в т.ч. на **локальной LLM**. Microsoft прямо пишет, что AI-оценки не должны быть единственным основанием для кадровых решений → нужен человек в контуре (апелляции).
→ **Нужно:** фронт на чистом HTML/CSS/JS как самодостаятельный компонент (без фреймворков, без глобальных стилей, конфиг API-адреса), бэкенд-адаптер.

### Б11. Доверие к AI и стоимость
Жюри проверит, что система **реально анализирует** новые диалоги (а не отдаёт заготовки). Для платной модели нужно указать название и стоимость одной оценки.
→ **Нужно:** лог вызова (модель, токены, время, стоимость), кнопка «переоценить», детерминированность (temperature 0), прозрачный промпт.

### Б12. Эскалация после бота = клиент уже раздражён
Почти каждый чат: бот ответил шаблонно → клиент просит человека → ожидание 0:20–2:30. Клиент приходит к оператору уже с контекстом и часто с раздражением («уже надоело», «Я уже писал»). Отсюда ценность критериев «Эмпатия» и «Выявление потребности с учётом известного».

## 3. Что заложено в DEV-наборе (ловушки для оценщика)

Набор параллельный: одни и те же сценарии в RU/KZ/EN, в «хорошей» и «плохой» вариации. Это тест на **согласованность между языками**.

| Критерий | Типичные «Нет» / ловушки | Типичные N/A |
|---|---|---|
| 01 Контакт (поздоровался на языке клиента **и** представился в первом ответе) | «Привет, где именно ищете?» без имени (ru-014); «Сәлем. Қай сайтқа…» (kz-008); «Open settings…» без приветствия (en-015) | — (N/A не разрешён) |
| 02 Потребность | переспрашивает уже известное (ru-014, ru-026, kz-008); отвечает не уточнив устройство/бумагу (ru-016, ru-018, en-015) | запрос понятен сразу (ru-001, ru-011, ru-012, ru-021…) |
| 03 Идентификация | раскрыл ограничение по счёту без проверки (ru-009, kz-015, en-014) | общие вопросы о тарифах/меню (большинство) |
| 04 Консультация 0–20 | ответил на 1 из 2 вопросов (ru-003 — комиссия; ru-007/en-007 — «когда повторить вывод»); «Всё есть в приложении» (ru-026) = 0 | клиент ушёл до формулировки запроса (ru-025) |
| 05 Эмпатия | грубость (ru-029), «Тогда не знаю» (ru-018), игнор недовольства | — |
| 06 Ведение 0–10 | невнятное «сверху вниз в меню» → клиент переспрашивает (ru-005); «Ну, тогда сайт» (ru-016); предупредил об ожидании (ru-028) = 10 | — |
| 07 Завершение | закрыл чат без прощания (ru-018, ru-026); «Bye.»/«Жақсы.» без итога (en-015, kz-005) | обрыв связи/клиент ушёл (ru-012, ru-025, en-009, kz-011) |
| 08 Грубые ошибки | деньги на личную карту (ru-022); частная платная консультация (ru-023, kz-013, en-013); оскорбление (ru-029); раскрытие конфиденциальных данных без идентификации (ru-009, kz-015, en-014) | — |

Спорные места, которые нужно зафиксировать правилом (и спросить у организаторов, если есть канал):
- ru-002: оператор запросил идентификацию, клиент отказался, данные не раскрыты → 03 = «Да» или N/A?
- ru-012 / en-009: оператор ответил, клиент сказал «всё», затем обрыв → 07 = N/A (нет возможности завершить) или «Нет»?
- Звонки: чек-лист называется «чек-лист качества **чатов**»; эталон по звонкам может не быть, контрольный набор — вероятно, чаты.

## 4. Выводы для продукта (приоритеты)

1. **Точность > всё остальное.** Структурированный JSON-ответ LLM по каждому критерию (ответ, ступень шкалы, id реплики-доказательства, обоснование), строгие определения из чек-листа + памятка «Нет vs N/A» в промпте, few-shot на ловушках выше, temperature 0, проверка валидности (N/A только где разрешён, шкала только из допустимых ступеней). Свой эталон по DEV → метрика совпадения при каждой правке промпта.
2. **Расчёт итога — кодом**, строго по стр. 2 чек-листа: да = вес, нет = 0; шкала × вес / max; N/A → пропорциональное перераспределение до 100; округление до 2 знаков; нет применимых → итог не считается; грубые ошибки отдельно.
3. **Динамический чек-лист** + версии: замена критерия на контроле за 1 минуту через UI → переоценка.
4. **Карточка диалога**: транскрипт с ролями/таймкодами, клик по доказательству → скролл + подсветка, плеер для звонков с переходом на время.
5. **Апелляции**: оператор → комментарий по критерию; проверяющий → подтвердить/изменить + причина; пересчёт; история.
6. **Список**: фильтры по языку/каналу/флагу грубой ошибки, итоговый балл, статус апелляции. Дашборд по критериям — бонус за «функциональность».
7. **README**: запуск в 3 команды, модель, стоимость одной оценки.
